CSV and JSON writes under `spark.sql.legacy.timeParserPolicy=LEGACY` format dates and timestamps as Spark does (its legacy patterns and the hybrid Julian/Gregorian calendar), and from the Spark 4.0 profile on the default timestamp write keeps the seconds of a zone offset (`spark.sql.files.supportSecondOffsetFormat`, new key `krishiv.io.text.secondOffsets`).
`schema_of_csv` and `from_csv` under `LEGACY` infer and read dates as Spark does; `from_csv` takes the `preferDate` option and, with the fallback off and no `dateFormat`, reads dates strictly as `yyyy-MM-dd`, like the CSV file reader.
JSON reads and writes, `from_json`, `to_json` and `schema_of_json` refuse a `locale` option other than `en-US` with `KRISHIV_UNSUPPORTED_FEATURE`, as CSV does: they read decimals with the US rule, where Spark parses them with that locale's `DecimalFormat` (`1.000,5` is 1000.5 under `de-DE`).
`to_json`, `to_csv` and `to_xml` write a `TIMESTAMP` with the file writers' default `timestampFormat`, `yyyy-MM-dd'T'HH:mm:ss[.SSS][XXXXX]`, so an offset keeps its seconds (`1880-01-01T00:00:00.000-07:52:58` in `America/Los_Angeles`), and follow `spark.sql.files.supportSecondOffsetFormat` as the writers do. `to_csv` prints the session zone for the `z` and `VV` letters (it printed `UTC`), and `to_json` takes a `dateFormat` that Spark only formats with (`EEE, d MMM yyyy`). `from_csv`, `to_csv` and `schema_of_csv` refuse a `preferDate` that is not `true` or `false` with `_LEGACY_ERROR_TEMP_2147` (except under `LEGACY`, where Spark does not read it), and an `enableDateTimeParsingFallback` that is not `true` or `false`.
