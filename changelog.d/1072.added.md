Nanosecond timestamp values (`TIMESTAMP_NTZ(7..9)`, `TIMESTAMP_LTZ(7..9)`, Spark 4.3) in hashing, aggregates, window frames, interval arithmetic, `unix_nanos`, `date_format` with 7-9 fraction digits and `current_timestamp(p)`; read and written in Parquet, JSON and CSV, carried by the plan codec and Spark Connect. Under the Spark 4.3 profile `unix_seconds`, `unix_millis` and `unix_micros` take a `TIMESTAMP_NTZ`.
Parquet reads and writes the nanosecond timestamp types as Spark 4.3 does: `INT64 TIMESTAMP(NANOS)` with each column's precision in the footer's Spark schema; without `spark.sql.timestampNanosTypes.enabled` such a file is refused (`FEATURE_NOT_ENABLED` / `PARQUET_TYPE_ILLEGAL`), and `spark.sql.legacy.parquet.nanosAsLong` reads a foreign file's nanoseconds as `bigint`.
Plans carrying the nanosecond timestamp types travel to workers (plan codec feature `timestamp_nanos_types`); an older worker refuses such a plan by name.
Spark Connect maps the 4.3 nanosecond timestamp types (`TimestampNTZNanos` / `TimestampLTZNanos`, precision 9 when absent, else 7 to 9 or `INVALID_TIMESTAMP_PRECISION`) both ways, and sends such columns as Spark does: `Timestamp(NANOSECOND)` in the session zone for LTZ, the precision in the field metadata.
JSON and CSV files, `to_json`, `to_csv`, `from_json` and `from_csv` read and write the nanosecond timestamp types as Spark 4.3 does: a write floors the value to its precision and prints the fraction digits the `timestampFormat` / `timestampNTZFormat` pattern has (milliseconds by default); a read keeps up to the precision's digits, takes only a string and never falls back to the default grammar after a pattern fails.
