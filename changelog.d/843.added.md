Iceberg write, part 2: appends commit through a loop that never retries blind. An unknown answer is checked against the table, and only the same attempt is resent, or the write is rebased once the branch has moved. A write whose outcome stays unknown deletes nothing. New manifests are grouped and rolled as Java's `writeDataManifests` does, and merged on the first attempt as `MergeAppend` does. The append sink and its open-file cap (`krishiv.iceberg.write.maxOpenFiles`, default 100) are in place, but no catalog commits through them yet (that comes with the catalog clients), so Iceberg tables stay read-only.
