# krishiv-session

**Layer:** L5 (may depend only on crates in L5 or lower; `cargo xtask layering`).
**Real code since:** P2-T090 (session, configuration, catalog, DataFrame actions).

## Purpose
The session every API surface shares: configuration, the session catalog (temporary tables and views),
and the query pipeline (parse → analyze → optimize → physical plan → run). The Rust facade (`krishiv`, L7)
re-exports it; the Python facade and the Connect and Flight SQL servers (L6) wrap the same type.

## Writers (Spark 4.0 `DataFrameWriter` is the reference)
- `saveAsTable` modes: `errorifexists` fails on an existing table, `ignore` leaves it, `append` adds by column name (a view, another format (the writer's default is `spark.sql.sources.default`), another column count or names, partitioning or bucketing are Spark's `_LEGACY_ERROR_TEMP_1158`, `1159`, `1161`-`1164`, checked in that order; bucketing is compared as options, so no `bucketBy` into a bucketed table is 1164), `overwrite` drops and recreates. `insertInto` is by position: `append`, `ignore` and `errorifexists` all append, `overwrite` is `INSERT OVERWRITE`. The format defaults to `spark.sql.sources.default` when `format()` was not called.
- The file formats the engine writes are Parquet, CSV, JSON, Avro and text (one string column); `orc` writes are `KRISHIV_UNSUPPORTED_FEATURE`.

## Extension points
- New DataFrame action: an async method in `src/dataframe.rs` running on the session executor; transformations only build IR.
- New config key: add it to the typed registry in `krishiv-common` (see that crate's map).

## Invariants
- One pipeline: no API surface plans or runs queries any other way.
- Nothing a config doc calls process-wide is built per session: it lives on `EngineRuntime` (the 50-session test in `tests/runtime.rs` checks it).
- Each query reads a snapshot of the configuration; a concurrent `conf().set` never changes a running query.
- Transformations only build IR; actions are `async` and run on the session's executor, so they work from
  any runtime. Dropping an action's future or result stream cancels its query.
- SQL-bodied temporary functions live in a per-session map (`sql_functions.rs`) replaced on every change (never edited); a
  query takes the map when it starts and reads one snapshot, and every change bumps the registry version.
- The IR is reachable only behind the `unstable-ir` feature (not covered by semver).
- A read of a permanent view analyzes the view's query once on its own (`Session::check_stored_views`) before the whole query, so its binding mode can check types and names (`INCOMPATIBLE_VIEW_SCHEMA_CHANGE`, `CANNOT_UP_CAST_DATATYPE`); `TYPE EVOLUTION`/`EVOLUTION` views store their new schema only after the whole query analyzed, with a compare-and-swap (a concurrent change wins). Difference from Spark (whose `ViewSyncSchemaToMetaStore` runs in every analysis, `.schema` too): a metadata analysis (`schema_for_metadata`, Connect `AnalyzePlan`, any role) returns the evolved schema but never stores it, since an `AnalyzePlan` must not write the catalog; the next ordinary query stores it (`views_schema_binding` `a_metadata_analysis_never_stores_the_evolved_schema`).
- Access control: one principal and one `AccessPolicy` per session, for life. Reads are checked in analysis; what a statement writes, creates or drops (`krishiv_sql::statement_targets`) is checked in `sql` before it is dispatched, and `df.write` paths before `DirectoryWrite::begin`, all through `krishiv_plan::analyzer::authorize` (fail closed, 42501, no reason, no existence oracle). Permanent views are inlined before binding, so `authorize_reads` asks the policy about every catalog-store lookup in plan order before any read (name as written and folded, then the view securable); a failure inside a stored view's text is raised only after that. The views read by the body of a SQL function a query calls are asked about after Bind (`authorize_body_reads`; the denial comes before the result or any failure in the view's text, but the tables inside the view are loaded first). Every denial logs one `krishiv::audit` record. A local path is asked of the policy, and named in the audit record, with its links resolved; the 42501 the caller sees names it as written, `..` folded from the text only (`access::Checked`), never anything read from the file system. Accepted: a path that cannot be resolved is denied without asking the policy, so with a remote policy it is answered faster than a missing one (a timing difference only; class and text are the same). Deny-all and inverse matrices: `tests/access_policy.rs` (merge-blocking).
- `#![forbid(unsafe_code)]`; no `unwrap`/`expect`/`panic` in library code; errors carry a Spark error class
  and SQLSTATE.
